# AGENTS.md

Guidance for AI coding agents working in this repository.

**Read [README.md](README.md) first.** It lists the tools the image ships, the versioning scheme and the license. This file does not repeat that. It covers how the repo works and the traps in it.

## What this repo is

This repo builds one Docker image, `autonomouslogic/base-image` on Docker Hub, and `Dockerfile` defines all of it. There is no application code, package manifest or test suite. Nothing from the repo is `COPY`'d into the image, so only `Dockerfile` changes affect what ships.

- `Dockerfile`: the image. Every pinned tool version lives here.
- `renovate.json`: regex managers that read the `# renovate:` comments in `Dockerfile`, plus package rules. Extends the shared preset [`autonomouslogic/renovate-config`](https://github.com/autonomouslogic/renovate-config).
- `Makefile`: `make docker` builds `autonomouslogic/base-image:dev` with `--pull`. `make run` builds it and opens `bash` inside. Note that `make run` bypasses the image entrypoint.
- `.github/workflows/build.yml`: CI job `Test`. It runs on every push to any branch, does `docker build` and then `docker run … uname`, and times out after 30 minutes.
- `.github/workflows/semantic-pr.yml`: rejects PR titles that are not Conventional Commits.
- `.releaserc`, `publish.sh`: release tooling (see [Commits, PRs, releases](#commits-prs-releases)). Not for local use.
- `CHANGELOG.md`: generated by semantic-release. Never edit it by hand.

## Dockerfile anatomy

- **Base image and `install-tool`.** The base is [containerbase](https://github.com/containerbase/base), on Ubuntu 24.04. Most tools are installed with its `install-tool <tool> <version>` command, which downloads prebuilt binaries and sets up shims and environment. The containerbase repo lists supported tools under `src/cli/tools/`. It also provides `install-npm`, `install-pip` and `install-gem`. Use `install-tool` in preference to hand-written installs.
- **Shell and environment in `RUN`.** The base image sets `SHELL ["/bin/bash", "-c"]` and `BASH_ENV=/usr/local/etc/env`. Every `RUN` is therefore bash and already has the PATH and environment set up by earlier `install-tool` steps. Don't add manual exports for containerbase tools.
- **Entrypoint and user.** At runtime the entrypoint is containerbase's `docker-entrypoint.sh`, which loads that environment and then runs `exec dumb-init`. No `USER` is set, so everything installs and runs as root.
- **Docker.** `install-tool docker` installs only the Docker CLI, with no daemon, so consumers must mount a host socket. Buildx comes from `COPY --from=docker/buildx-bin`. `docker buildx install` then makes `docker build` use buildx.
- **Rust.** Rust does not use containerbase. rustup installs `ARG RUST_VERSION` into `CARGO_HOME=/usr/local/cargo` and `RUSTUP_HOME=/usr/local/rustup`. rustfmt comes from `rustup component add` and sleek from `cargo install`. `rustfmt`, `cargo-fmt` and `sleek` are also copied into `/usr/local/bin`. The first two copies are rustup proxies that still need `RUSTUP_HOME` and the toolchain, so don't delete the rustup directories to slim the image.
- **apt packages.** `gh` comes from GitHub's apt repo. It is installed in a single `apt-get` layer together with `jq`, `build-essential` and `wget`, and that layer cleans the apt lists at the end. Add new apt packages to this same layer.
- **Working directories.** `WORKDIR` is `/usr/src/build` while tools install and `/usr/src/app` at the end, which is where consumers mount their projects. `git config --global --add safe.directory /usr/src/app` applies to root and to that path only.
- **Duplicated tools.** The base image already ships git and jq. The explicit `install-tool git` line pins the git version this image uses.
- **Labels.** The `LABEL` block does not set `org.opencontainers.image.version`, so the value inherited from the base image (containerbase's own version) shows through.

### Unpinned inputs

Renovate does not track the following, so rebuilding the same commit can pick up newer versions of them:

- `docker/buildx-bin`, which is referenced without a tag. `publish.sh` builds without `--pull`, so a release uses whatever `latest` is cached on the release host.
- `sleek`, which is always the latest version from crates.io.
- The rustup installer script.
- The apt packages `gh`, `jq`, `build-essential` and `wget`.

If you pin one of these, give it a `# renovate:` annotation so that it keeps updating. containerbase supports `install-tool gh` and `install-tool buildx`.

## Renovate annotations

Most bugs in this repo have come from these annotations. Renovate updates a version only if the line directly above it is a `# renovate:` comment that matches one of the two regexes in `renovate.json`. An annotation that doesn't match causes no error, and the version silently stops updating. Terraform's first annotation used `packageName=` and was never picked up until the fix in 1.3.1.

These are the only two accepted shapes. The keys must appear in exactly this order, and the bracketed ones are optional:

```dockerfile
# renovate: datasource=<datasource> [lookupName=<package>] [versioning=<scheme>]
RUN install-<tool|npm|pip|gem> <name> <version>

# renovate: datasource=<datasource> [depName=<package>] [versioning=<scheme>]
ARG <NAME>=<version>
```

- **`RUN install-*` form.** `<name>` may contain only lowercase letters and `-`. If the upstream package name differs from `<name>`, set it with `lookupName=`, as in `lookupName=git/git` or `lookupName=hashicorp/terraform`. Do not use `packageName=`, even though examples from containerbase and Renovate do: this repo's regex does not recognise it.
- **`ARG` form.** Set the package with `depName=`, as in `depName=rust-lang/rust`.
- **Versioning.** The default is `semver`. Use `versioning=docker` when versions come from Docker image tags (node, docker, terraform) and `versioning=gradle` for Gradle.
- **Version strings.** Write them exactly as the datasource reports them, for example `v2.55.0` for git tags and `25.0.4+101.0.LTS` for Adoptium.
- **No annotation needed.** Renovate's built-in managers handle `FROM` and the GitHub Actions versions.

After touching any annotation, run this check. It needs only Node, prints each match and exits non-zero if any `# renovate:` comment fails to match:

```bash
node -e '
const fs = require("fs");
const cfg = JSON.parse(fs.readFileSync("renovate.json", "utf8"));
const df = fs.readFileSync("Dockerfile", "utf8");
let hits = 0;
for (const m of cfg.customManagers ?? cfg.regexManagers)
  for (const s of m.matchStrings)
    for (const x of df.matchAll(new RegExp(s, "g"))) { hits++; console.log(JSON.stringify(x.groups)); }
const total = (df.match(/# renovate:/g) || []).length;
console.log(`${hits}/${total} renovate annotations matched`);
process.exitCode = hits === total ? 0 : 1;
'
```

## Renovate behaviour

- **Grouping and schedule.** The shared preset puts all minor and patch updates into one PR called "update all non-major dependencies". That PR is created on the first Monday of each month. Major updates get separate PRs as soon as they appear.
- **Automerge.** `renovate.json` enables automerge for every update, majors included. The only functional check is the `Test` job, which checks just that the image builds and runs `uname`. An update that breaks a tool at runtime will still merge and ship.
- **Java.** Java (`adoptium-java`) has its own group because Adoptium sometimes lists versions before they can be installed. For example, `25.0.4+101.0.LTS` failed CI when first offered and built fine a few weeks later. A failing Java PR is usually transient, so keep Java in its own group.
- **Legacy config keys.** `renovate.json` still uses the legacy `regexManagers` and `fileMatch` keys, and Renovate may open a `chore(config): migrate config` PR. The migrated regex captures into a `packageName` group, but the Dockerfile annotations still say `lookupName=`. The check script works with both formats.
- **Debugging.** When a version isn't updating, look at the Dependency Dashboard issue on GitHub. It shows detected dependencies and lookup errors.

## Commits, PRs, releases

- **PR titles.** Titles must be Conventional Commits. PRs are squash-merged, so the title becomes the commit that decides the release. The maintainer capitalises the subject, as in `feat: Terraform`, `fix: Rust install via Rustup` and `chore: Fixed Terraform Renovate expression`.
- **Release impact.** Each commit type bumps the version as follows. These are the semantic-release defaults plus one custom rule in `.releaserc`:

  | Commit type | Release |
  |---|---|
  | `feat` | minor |
  | `fix`, `perf` | patch |
  | `chore(deps)` (the custom rule) | patch |
  | `!` or `BREAKING CHANGE` | major |
  | `chore`, `docs`, `ci`, `build`, `refactor`, `style`, `test` | no release |

  In past practice, adding a tool is `feat` and fixing how a tool is installed is `fix`. Changes only to Renovate config are `chore` or `ci`; they don't change the image, so they don't release. Tool version bumps, majors included, are `chore(deps)`.
- **Merging to `main` publishes a release.** semantic-release runs outside GitHub Actions: there is no release workflow in this repo, and `.releaserc` sets `"ci": false`. Each release does the following:
  - commits `chore(release): X.Y.Z [skip ci]` with the updated changelog
  - tags `X.Y.Z` (no `v` prefix)
  - creates a GitHub release
  - runs `publish.sh`, which pushes `:X.Y.Z` and `:latest` to Docker Hub (`linux/amd64` only)
- **Never** run `publish.sh` or semantic-release, push tags or edit `CHANGELOG.md`.
- **Breaking changes.** Every release overwrites `:latest`. Removing a tool, or changing install paths, the default user, `WORKDIR` or the entrypoint, breaks consumers immediately. Raise such changes with the maintainer before choosing a commit type.

## Checklist: adding, removing or changing a tool

1. Update the tool list in README.md in the same PR.
2. Choose the install method in this order: `install-tool` first; otherwise an `ARG` version with an install step; apt only for utilities that don't need a pinned version.
3. Add the `# renovate:` annotation and run the check script above.
4. Build the image and run the smoke test below. Add the new tool to that command in this file.
5. Title the PR `feat: <Tool>` when adding a tool. Removing one is breaking, so ask first.

## Verifying a build

CI proves only that the image builds and runs `uname`. After any `Dockerfile` change, check that the tools actually work. This command goes through the real entrypoint, which `make run` does not:

```bash
make docker
docker run --rm autonomouslogic/base-image:dev bash -c 'set -e
  git --version; node --version; npm --version; yarn --version
  docker --version; docker buildx version
  java -version; gradle --version; mvn --version
  rustc --version; cargo --version; rustfmt --version; sleek --version
  terraform version; gh --version; jq --version
  gcc --version; make --version; curl --version; wget --version'
```

A CI build takes a couple of minutes, including compiling sleek from source. The job times out at 30 minutes, so any new heavy install needs to stay well under that. If there is no Docker daemon, which is common in agent sandboxes, say so rather than claiming the image builds. Pushing a branch runs the `Test` job.
